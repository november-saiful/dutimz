# DUTIMZ — ঢাকা বিশ্ববিদ্যালয়ের সংবাদমাধ্যম

মোবাইল-প্রথম, বাংলা-শুধু ঢাকা বিশ্ববিদ্যালয় নিউজ পোর্টাল।

## Architecture

- Next.js 15 App Router portal (React + Tailwind + shadcn) deployed to Cloudflare Workers via `@opennextjs/cloudflare`. Every route renders inside the dashboard shell (sidebar + inset header + cards + chart).
- A separate Cloudflare Worker authenticates media requests, resolves every asset through the audited `get_media_asset` (news) and `get_spotlight_media` (forum) database functions, and reads/writes two private R2 buckets: `dutimz-media` for news and `dutimz-spotlight` for the forum. Every uploaded image is re-encoded to WebP at quality 85 by Cloudflare Images, and the smaller result replaces the uploaded file, so the storage saving is real. If the transform cannot be verified as a smaller WebP, the original is kept unchanged; non-image uploads are stored as-is.
- Supabase Auth (Google only) and Postgres. All production schema edits are committed SQL migrations protected by RLS.
- GitHub Actions is the production release controller **and the only gate in front of production**: a push to `main` runs typecheck, the database tests, the production build and the interface tests, and the release job starts only once that same commit passed all of them (this repository has no pull-request review step, so a red `verify` is what stops a release). The release then builds the production bundle, applies Supabase migrations, deploys the media Worker, deploys the portal Worker, and walks the live site. Disable separate automatic production deployments in both Cloudflare and any linked provider integrations.

## Local development

1. Install Node.js 22+, npm, Docker, and the Supabase CLI.
2. Install dependencies:

   ```bash
   npm ci
   npm ci --prefix worker
   ```

3. Create a Supabase project (or run `supabase start`). Enable **Google only** under Authentication → Providers → Google, and add the local callback URL `http://localhost:3000/auth/callback/` to the Supabase and Google OAuth redirect allowlists.
4. Copy `.env.example` to `.env.local` and set the Supabase project URL and publishable/anon key. These are public browser credentials; never put a secret/service-role key in a `NEXT_PUBLIC_` variable or the Git repository.
5. Start the site: `npm run dev`. Local editorial preview content is clearly marked as illustrative. To use live content, migrate/reset the local database and set `NEXT_PUBLIC_DEMO_MODE=false`.
6. Start the local Supabase stack and apply/test migrations with `supabase start`, `supabase db reset`, and `supabase test db`.
7. Preview the Workers runtime with `npm run preview` (builds with OpenNext and serves locally). Wrangler uses local bindings by default, so the cache bucket and the revalidation queue are simulated too: a second request to a route that exports `revalidate` reports `x-nextjs-cache: HIT` there and nowhere else, because `next dev` and `next start` have no incremental cache at all. A response that reports `MISS` every time means the bindings are not reaching the Worker. The standalone media service can be run with `npm run dev --prefix worker` once local Worker secrets are configured.

## Supabase configuration

- Initialize/link the production Supabase project in your own environment. Add `SUPABASE_PROJECT_ID`, `SUPABASE_DB_PASSWORD`, and `SUPABASE_ACCESS_TOKEN` as protected GitHub production secrets. The production environment must require an explicit approval reviewer.
- Enable the Google Auth provider. Only `openid`, email, and basic profile scopes are needed. Until the `www` redirect rule is active, allow both `https://dutimz.com/auth/callback/` and `https://www.dutimz.com/auth/callback/` in Supabase Auth and the Google OAuth redirect URI list; after enforcing the apex redirect, the apex callback can be the sole site callback. Keep any explicitly configured Supabase custom Auth domain too.
- The schema and authorization policies are in `supabase/migrations`. For local work use `supabase db reset`; never apply ad-hoc production SQL. Do not connect the Google OAuth identity provider to user roles—sign-up defaults to `reader`.
- Administrator rights are configured data, not a race for a single claim. `public.app_settings.bootstrap_admin_emails` holds a comma separated list of the Google addresses that are administrators; migration 007 hands a listed address the `admin` role in the same transaction as its first sign-in, and `public.bootstrap_admin_accounts()` reconciles owners who signed in before the list was configured. A signed-in caller can only ever promote its own listed account, so an ordinary reader cannot use it to hand out rights. Migration 008 folded the retired `initial_admin_email` address into the list and dropped that key, so the list is the only source of administrators — a second setting can no longer disagree with it out of sight.
- The addresses are personal data and this repository is public, so they are not committed. They travel from the `BOOTSTRAP_ADMIN_EMAILS` repository secret into the database through the Supabase management API in the release workflow (`scripts/sync-bootstrap-admins.mjs`), which also fails the release unless every configured address that has an account holds the administrator role. Adding an owner is therefore a secret update plus a release. Removing one never demotes anybody: a role change stays a deliberate, audited `assign_user_role` action. The admin panel reflects all of it: it lists the accounts that hold the administrator role with who last handed it to them, the addresses the release configured (through `admin_bootstrap_addresses()`, which returns nothing to a non-admin) including owners who have not signed in yet, and every recorded role change from `admin_audit_log`. Do not enable anonymous role management.
- The desk runs from `/account/admin` and is organised into four tabs. **সদস্য** lists members from `admin_member_records` with sortable columns, search and paging, and the row carries the member's wallet — held, available and reserved — taken from the same ledger sums the member sees on their own balance page, so the two cannot disagree. Money is adjusted from a wallet button on that row (or from a name search in the finance tab): nothing in the panel ever asks a person to paste a member id. That same dialog lists the member's ledger — each entry's type, amount and date, newest first, read straight from `earnings_ledger` under `ledger_owner_or_admin_read` — so the desk sees why a balance is what it is, not only what it is, before changing it. **প্রতিবেদন** is the story surface, which is why the panel can manage news at all: it lists every article whatever its status (allowed because `articles_published_read` grants the desk select on all of them), and edits or re-dates a story through the audited `admin_update_article` and `admin_set_article_publication`. Taking a live story down and putting it back goes through `admin_set_article_status`, which accepts only `published` or `rejected`: a story is never quietly returned to a queue it can no longer be waiting in, and restoring one keeps the dateline it went live with and never pays the reporter twice. **স্পটলাইট** hides or removes a forum post, and **অর্থ** lists the pending withdrawal requests as a queue that opens each member's wallet — the decision itself happens in that dialog, next to the balance the request is holding, through the audited `review_withdrawal` and only with the `paid`/`rejected` values that function accepts. A member whose wallet holds a request is marked on their row. Approval of new submissions still lives on `/account/moderation`, which lists pending articles only.
- Signing in lasts as long as a cookie can: the OAuth callback forwards the cookie options Supabase hands it and both the callback and `lib/supabase.ts` pin a 400-day `maxAge` (the browser ceiling), so the auth cookie is persistent rather than a session cookie that dies when the browser closes. `lib/supabase.ts` also exposes `isMissingSession`, so a dropped network call is reported instead of being mistaken for a sign-out. True "forever" depends on the project's refresh-token expiry under Authentication settings; keep it non-expiring with rotation.
- Spotlight is an issue tracker. A post stays `open` until its author or the desk decides; `mark_spotlight_issue` is the only way to move it, it refuses anyone else with `42501`, and it demands the detail each state needs — a solve names the body and the time bucket and may carry proof pictures, work-in-progress names the body behind it, and `invalid` requires the reason. Every mark appends a row to `spotlight_issue_events` and an entry to `admin_audit_log`; visibility (`visible`/`hidden`) is a separate axis the desk still owns. Proof images ride the existing Spotlight upload pipeline and resolve through `get_spotlight_media`, which now accepts resolution attachments too.
- Spotlight accountability is public. `/statistics` renders `get_public_spotlight_stats()` and `get_public_spotlight_solvers()`, both granted to `anon`: solved-to-raised over this week, month, year and all time, a leaderboard of which body solved how many, and a false-issue count. The windows count the issues *raised* in the period that are now solved, so a solve is never credited to a later week.
- Members get their own record on `/account`: **পরিচয়** keeps the summary and actions, **আমার সংবাদ** lists the member's own stories by status through `get_my_articles()` with the reason on a rejection, and **আমার স্পটলাইট** lists their issues with a filter per issue state. Rejected and unsettled items stay private to their owner; nothing here is exposed publicly.
- Actions that finish away from the field being filled in report through a small dependency-free toast (`components/ui/toast.tsx`, mounted once in the root layout), and the story form's submit button shows a spinner and `aria-busy`. The phone dock's centre button uses the site's own mark (`public/brand-icon.svg`) rather than a generic icon.
- Update the quality-gated Google sign-in, RLS, and workflow tests as schema migrations evolve.

## Cloudflare setup

Create a Cloudflare Workers project named `dutimz` and two private R2 buckets: `dutimz-media` for news images and `dutimz-spotlight` for forum photos. The two cache buckets (`dutimz-cache` and `dutimz-cache-preview`) do not need creating by hand: the release and the pull-request job run `scripts/ensure-cache-buckets.mjs`, because `wrangler deploy` binds a bucket by name rather than creating one. They hold rendered pages and nothing else, and deleting one only costs a re-render. `dutimz.com` and `www.dutimz.com` are connected to the Worker as Custom Domains by `routes` in `wrangler.jsonc`, so a release re-asserts that binding instead of leaving it to a manual dashboard step; configure `media.dutimz.com` to route to the `dutimz-media` Worker. Enable the Cloudflare Images binding for image processing. Keep the Cloudflare Redirect Rule for `www.dutimz.com/*` to `https://dutimz.com/$1` with status 301 as a second layer; the Next.js `middleware.ts` also redirects dynamic requests on the `www` host to the apex. The public `_redirects` file only handles path redirects. The portal Worker holds no binding to the media buckets: all media is written and served by the media Worker, so the site cannot read a media key even though it now owns a bucket of its own for the page cache.

`wrangler.jsonc` is the source of truth for the portal Worker configuration, which means the Cloudflare dashboard is **not**: non-secret vars live in the file, and anything set only in the dashboard is shadowed rather than merged. Because of that:

- `NEXT_PUBLIC_SITE_URL`, `NEXT_PUBLIC_MEDIA_URL`, and `NEXT_PUBLIC_DEMO_MODE` are inlined into the bundle **when the build runs**, so the build environment decides them and the identical `vars` in `wrangler.jsonc` are inert for those names (they are kept as documentation). The fallbacks in `lib/site.ts` apply whenever the build exports them empty; empty therefore always means unset, and no workflow should export these as an empty string.
- `NEXT_PUBLIC_SUPABASE_URL` and `NEXT_PUBLIC_SUPABASE_ANON_KEY` are credentials baked in at build time, so they are not committed. The release workflow calls `scripts/inject-worker-vars.mjs`, which writes them (from the GitHub repository variables or secrets) into an untracked `.env.production` file in the ephemeral runner just before `opennextjs-cloudflare deploy`. Deploying by hand therefore needs those two variables exported, and the script refuses to write them outside CI.
- The media Worker verifies every upload token against Supabase, so it needs the same `SUPABASE_URL` and `SUPABASE_ANON_KEY`. It is a separate deployment with its own bindings, so the release writes them with `wrangler secret put` immediately before `wrangler deploy --config worker/wrangler.jsonc`, reading the identical GitHub variables the portal builds from. They used to be set only by hand in the dashboard, where they could silently stop matching the portal's values — a mismatch the Worker can only report as a bare `401` to a signed-in reader. `worker/wrangler.jsonc` never carries them.
- Uploads take their bearer token from `freshAccessToken()` in `lib/supabase.ts`, never from the raw stored session. `getSession()` returns the cookie session without refreshing it, so a session past its one-hour access token still looks signed in while every request it authorises is refused; the helper refreshes first and hands back a token that works now.
- The deploy step exports those two values as well as writing the file, because a *empty* variable in the environment is inlined as an empty string and wins over `.env.production` — that combination once published a production build that served illustrative content with blank media URLs.
- A release is ordered so that nothing irreversible happens before the steps that can fail on their own. The ref guard and the credential check run first: a missing or rotated secret costs one red step, not a migrated database with no matching deployment. Then the production bundle is built with the production credentials inlined, and only then are migrations applied — the build is the step most likely to fail for a reason no earlier job could see, and failing it before `supabase db push` keeps the schema from running ahead of the code that understands it. `opennextjs-cloudflare deploy` deliberately does not build, so what ships is exactly the bundle that passed, not a second build later in the same job.
- The release job ends with a summary table recording which stages landed, so a red run says whether production was touched at all instead of leaving only a failed step somewhere in the log. Before the migrations are applied — an earlier step than that table, because a plan published afterwards describes what already happened to the database rather than what is about to — the same run page carries what `supabase db push --dry-run` answered for this commit. A push to `main` therefore says which migrations it is about to move, the way a pull request would have shown them, instead of leaving the plan in a step log nobody opens. A manual `workflow_dispatch` must run on `main`; on any other ref it fails in that first step without changing anything.
- `env.preview` pins preview deployments to `NEXT_PUBLIC_DEMO_MODE: "true"` and the preview build is given no Supabase credentials at all, so unmerged pull-request code renders demo content and can never read the production database. Set the `PREVIEW_SUPABASE_URL` and `PREVIEW_SUPABASE_ANON_KEY` repository variables to point previews at a staging project instead.
- `open-next.config.ts` is required by the adapter, which refuses to build without it. It wires the R2 incremental cache and the Durable Object revalidation queue. Both have to be wired explicitly: the adapter resolves `incrementalCache`, `queue` and `tagCache` to no-op implementations when they are not overridden, and a bare `defineCloudflareConfig()` is therefore a valid, buildable, **wholly uncached** deployment. That is what production ran: every public page re-rendered from the database on every request and the article route answered with `Cache-Control: no-store`. No tag cache is configured because nothing calls `revalidateTag`/`revalidatePath` yet, and no regional cache wrapper is used because its one real benefit — bypassing the tag cache on a hit — is worth nothing while the tag cache is a no-op.
- `routes` declares `dutimz.com` and `www.dutimz.com` as Custom Domains, so a release re-asserts them rather than silently leaving them on a retired project. A hostname can only be attached while no other project owns it, so remove it from an old Pages project first — otherwise `wrangler deploy` fails with the hostname already in use. The `preview` environment clears `routes`, so a pull-request preview can never claim the production hostnames.
- Media Worker R2 binding: `MEDIA_BUCKET`; Cloudflare Images binding `IMAGES`; public variables `SUPABASE_URL`, `SUPABASE_ANON_KEY`, and `ALLOWED_ORIGINS` (a comma-separated exact-origin allowlist, including both apex and `www` site hosts).
- Portal Worker caching bindings: R2 `NEXT_INC_CACHE_R2_BUCKET` (the `dutimz-cache` bucket), Durable Object `NEXT_CACHE_DO_QUEUE` bound to the `DOQueueHandler` class with the `v1` migration that creates it, and the `WORKER_SELF_REFERENCE` service binding the queue calls the Worker back through to regenerate a stale page. All three are needed together: the cache without the queue can never regenerate a stale entry, and with neither the adapter silently re-renders everything. `observability` is enabled on this Worker, so `reportError`'s output is queryable instead of write-only. Bindings are **not** inherited by environments, so `env.preview` re-declares each one against `dutimz-cache-preview` and points its self reference at `dutimz-preview` — the name `deploy --env preview` actually publishes.
- Worker secret `SUPABASE_JWT_SECRET` is deliberately not used. Verify user access by calling Supabase Auth's `/auth/v1/user` endpoint with the presented bearer token; do not trust unsigned claims.
- Bindings and variables must be configured for production **and** preview environments. Keep a separate staging Supabase project and media bucket when possible.

Configure private Worker keys with Wrangler secrets, not in `wrangler.jsonc`. Disable the zone's **Email Address Obfuscation** (Scrape Shield) so the published contact address stays readable rather than being rewritten into a `/cdn-cgi/l/email-protection` link.

Configure the GitHub Actions repository variables (or secrets, the release workflow accepts either) `SUPABASE_URL` and `SUPABASE_ANON_KEY`, and the protected secrets `SUPABASE_ACCESS_TOKEN`, `SUPABASE_DB_PASSWORD`, `SUPABASE_PROJECT_ID`, `CLOUDFLARE_ACCOUNT_ID`, `CLOUDFLARE_API_TOKEN`, and `BOOTSTRAP_ADMIN_EMAILS` (the comma separated list of the portal owners' Google addresses). Use a least-privilege Cloudflare token limited to the needed Workers/R2/Images resources. The Worker’s dashboard-based **Builds/automatic production deployments must be disabled** so GitHub Actions is the single trigger. The release refuses to start if any of those is empty, and names every one that is missing, so a rotated secret fails in seconds without touching production.

The release ends with `scripts/verify-live-config.mjs`, which polls the live configuration (a deployment serves requests before it serves its own configuration) and then repeats a signed-out visitor's anonymous reads against Supabase REST. That last part is not decoration: a row level security policy that calls a function the `anon` role cannot execute refuses the entire query with `42501`, so a missing `grant execute` takes the whole public feed down while the site still returns HTTP 200. Run it locally with `node scripts/verify-live-config.mjs`.

It checks the public domain first and, when that domain is still serving a previous project — moving a custom domain between Pages and a Worker is a manual Cloudflare step, not a build failure — falls back to the address Cloudflare gives the Worker itself and reports the exact action as a warning. A deployment that answers on neither host, or that serves demo content, still fails the release, so a red run always means something is genuinely broken.

Between the two it also walks the deployment the way a visitor would. The home page, the static pages, and a live article and section taken from the home page must all answer `200` on their canonical URL with **no** redirect and with the `public/_headers` guarantees attached; the unslashed form of an article must still settle on its canonical URL in one hop; and `www` must redirect to the apex without dropping the path. Those assertions are not padding. When the site moved off Pages, `public/_redirects` and Next.js disagreed about trailing slashes and every article, section and profile URL looped forever in the browser, while pages the Worker rendered shipped without any of the security headers the asset layer applies from `public/_headers` — and neither fault was visible to a check that only read the configuration. Run it locally with `SITE_URL=https://dutimz.com node scripts/verify-live-config.mjs`. It also proves the page cache is doing something, because the same misconfiguration is invisible to a check that only asks whether a page answered. The adapter's incremental cache and queue both default to no-ops, so a deployment can return `200` everywhere while re-rendering every public page from the database on every single request. Each cacheable route is therefore requested twice and the second response has to be served from the cache. Two checks are gated, because neither can be explained away: a fully static page (`/about/`) has to report `HIT`, since it can never be legitimately stale, and `/` — which exports `revalidate` and is prerendered — has to report `HIT` or `STALE` rather than `MISS`. The routes under `[slug]` are reported but not gated: they only carry a cache state once their params have been prerendered, and the build lists only a bounded slice of them. Finally it reads `robots.txt` and fails when an advertised sitemap does not answer `200`: the Astro era ended with `robots.txt` pointing at a sitemap the port had deleted, and nothing noticed because nothing looked. The sitemap itself (`app/sitemap.ts`) is generated from `SITE_URL` so the pointer and the file cannot drift apart again, is rendered per request rather than frozen at deploy time, and lists the published articles, the sections the database reports as live, and the static pages — nothing reader-specific.

## Important MVP business rules

- Reporter fees are issued exactly once on the first successful publication: junior ৳৯০, general ৳১১৫, executive ৳১৪০. Only assigned reporters earn article fees; a moderator receives a fee only when separately assigned a reporter tier.
- Profile details below ১০০% create held fees; completing every applicable field releases held money.
- Minimum withdrawal ৳৩,০০০; the first successful withdrawal also requires at least ৩৫ distinctly published articles. A pending request reserves balance; admin rejection refunds the reserve.
- Every moderation, role assignment, withdrawal review, and administrative money adjustment is logged with a reason. The role and member-record form does not force the desk to type one: a blank field records that no reason was given, so the audit log always says something rather than nothing. The moderation, withdrawal and balance forms still ask for one.
- Slugs are generated from the Bengali headline by phonetic transliteration (`slugify_title`), so reporters never type one: `ঢাকা` becomes `dhaka`, `সংবাদ` becomes `songbad`. A headline already in use claims the next numeric suffix. A published address never changes, so links keep working after a correction.
- Corrections transparency: every edit to a published story is public at `/corrections/` with its reason, editor label, and whether the headline or body changed. The raw revision history stays private and is exposed only through the `list_corrections` function.
- Images are re-encoded to WebP on upload and the compressed object replaces the uploaded file, so R2 keeps only the served copy. The transform runs through Cloudflare Images, which exposes no provable lossless mode; quality 85 is visually near-identical. Media that cannot be transformed stays as uploaded.
- Pages are cached by their own window: 30 seconds for the home page, 60 for an article and a section. On a `[slug]` route that window only means anything once the route is statically generatable, which for Next means `generateStaticParams` — the `revalidate` export on its own leaves the route classified as dynamic and re-rendering from the database on every request. The build therefore lists the newest 50 stories and the live sections; every other published slug is still rendered on demand and cached by the same window.
- A member's username is a stable handle: no authenticated client may change it, and only the desk can through the audited `admin_update_member` RPC. A handle is 3–24 characters of English letters, digits and underscores, starting with a letter — the member dialog checks that rule before calling and says which part failed, because the RPC's own refusal reaches the desk as fixed Bengali text and cannot explain itself. A profile is edited from one modal on the dashboard, and its public visibility is a per-field choice — name, username and profile picture are always public.
- The account menu is deliberately short: signed out it offers Google sign-in and saved content; signed in it offers the dashboard, the public profile and log out.
- A story's short description is derived from its body and is never typed by the reporter, but `p_excerpt` is still a required argument of `submit_article` — PostgreSQL will not let it default, because a defaulted parameter cannot be followed by a required one and the body comes after it. Every caller therefore has to send it, passing null to mean "derive it". Omitting the key does not fail validation: PostgREST matches a function by the argument names in the request, so it matches nothing and answers 404 "Could not find the function", which is how a working writer form silently stopped being able to publish.
- The database suite (`supabase test db`) covers the rules that are easy to regress silently: excerpt derivation, public-profile visibility, and the Spotlight submission and moderation limits. Adding a rule means adding its assertion and bumping `plan(N)`; `tests/pgtap-plan.test.mjs` fails the release if the plan and the written assertions disagree, or if a covered rule's description disappears.
- Spotlight (`/spotlight`) is a forum any signed-in member may post to with a title, a description and up to ten photos, stored in the forum bucket. An author may remove their own post; the desk may hide a post (a reversible, auditable state) or remove it outright from the dashboard's Spotlight tab. Spotlight media object keys are never readable by a client — the Worker resolves them through `get_spotlight_media`. The feed pages fifteen posts at a time behind an "আরও দেখুন" button rather than stopping at a fixed ceiling.
